# Agent 评价标准（6.2 设计）

## 目的

这套标准用于评价 Agent 对一条未参与岗位画像的测试 JD 所生成的完整结果，包括重点识别、事实匹配、调整建议、风险提示、自我介绍和岗位级简历草稿。

评价关注“结果是否可信且有用”，不把关键词数量多、文字长或分数高视为效果好。当前阶段由人逐条评分；后续可以把评分表做进页面，但评分标准本身保持不变。

## 评分前准备

每条测试 JD 先由人建立一份最小参考答案，Agent 不能读取这份答案：

- 标出 3～5 项真正重点，并注明来自岗位职责、任职要求还是加分项。
- 标出该岗位相较同方向岗位特别强调的 1～3 项内容。
- 列出允许引用的项目事实 ID，以及必须禁止或需要加限定的事实。
- 写一句“这份简历最应该突出什么”，作为评价时的判断基准。

同一位评价者先写参考答案，再查看 Agent 输出，避免被 Agent 的表达反向影响判断。

## 单条结果评分表

每个维度 0～4 分，总分 20 分。不能只记录总分，必须保留各项分数和一句理由。

### A. 是否识别真正重点

| 分数 | 判断标准 |
| ---: | --- |
| 4 | 参考答案中的主要重点基本齐全，优先级合理；职责、硬要求、加分项和市场补充区分清楚 |
| 3 | 主要重点大部分正确，有一项遗漏或轻微排序问题，但不影响简历方向 |
| 2 | 命中一部分重点，同时遗漏关键要求或把次要内容放得过高 |
| 1 | 主要依赖关键词罗列，重点与次要信息混在一起 |
| 0 | 核心方向判断错误，或输出与 JD 主要工作明显无关 |

判断时以目标 JD 的职责和任职要求为主，同类岗位画像只能补充解释，不能替代当前 JD。加分项不得当作硬性缺口。

### B. 是否引用正确项目事实

| 分数 | 判断标准 |
| ---: | --- |
| 4 | 所有重点都有正确事实 ID 或明确标为缺口；事实含义、状态、项目归属和可写范围均正确 |
| 3 | 主要映射正确，存在一处较弱但仍相关的事实，且没有越过真实性边界 |
| 2 | 有正确映射，也有明显牵强映射；需要人工较多修正 |
| 1 | 多数只是关键词相同，事实并不能证明相应能力 |
| 0 | 引用了错误项目、禁止事实，或把计划、背景、失败描述当作已完成能力 |

“事实内容已验证”和“项目事实卡已确认可进入简历”是两件事。卡片仍为草稿时，可以用于分析预览，但必须明确提示暂不可写入正式简历。

### C. 不同岗位是否有明显差异

这个维度必须使用至少两条不同方向或明显不同侧重点的 JD 成对评价，不能只看一条。

| 分数 | 判断标准 |
| ---: | --- |
| 4 | 重点排序、项目选择或项目表述、自我介绍均随岗位合理变化，同时保留确实通用的事实 |
| 3 | 至少两个关键部分发生合理变化，整体侧重点清楚 |
| 2 | 只替换岗位名称或少量关键词，项目主体描述基本相同 |
| 1 | 两份输出高度相似，差异不足以帮助投递 |
| 0 | 输出完全相同，或差异方向与两条 JD 相反 |

不能为了追求差异而虚构新经历。相同事实确实适用于两个岗位时允许重复，但“为什么突出它”和排序应该随岗位变化。

### D. 是否出现虚构或夸大

| 分数 | 判断标准 |
| ---: | --- |
| 4 | 所有事实性表述均可追溯；缺口、计划和限制表达准确，没有擅自补全指标、用户、上线或熟练度 |
| 3 | 没有虚构，仅有一处措辞略强，人工收紧后即可使用 |
| 2 | 出现无法由事实直接支持的推断，但尚未形成明确成果或能力承诺 |
| 1 | 出现一处明确夸大，例如把本地运行写成上线、把试用写成熟练掌握 |
| 0 | 出现虚构项目、职责、数据、公司经历、用户成果，或使用了“禁止写入简历”的内容 |

这是安全门槛：该项低于 3 分时，单条结果直接不合格；出现虚构事实、虚构指标或引用禁止内容时记为严重错误，不能用其他维度的高分抵消。

### E. 修改理由是否合理

| 分数 | 判断标准 |
| ---: | --- |
| 4 | 每个重要调整都能形成“JD 原文 → 岗位重点 → 项目事实或缺口 → 修改动作”的完整链路 |
| 3 | 主要修改有具体依据，少数理由较泛，但结论仍可复查 |
| 2 | 理由方向基本正确，却常停留在“提高匹配度”等通用表述 |
| 1 | 理由与修改内容联系弱，或把市场常见要求误说成当前岗位硬要求 |
| 0 | 没有理由、理由与 JD 冲突，或用错误事实为修改辩护 |

合理理由应指出具体 JD 证据和事实证据。不能把“同类岗位常见”直接写成“该岗位要求”。

## 一票否决项

出现以下任一情况，单条结果记为不合格，并单独记录错误类型：

- 虚构项目、工作经历、功能、指标、真实用户、部署状态或第三方认可。
- 引用了事实卡中“禁止写入简历”的内容。
- 把“计划实现”“需要补充”写成已完成。
- 当前 JD 未要求、个人也无事实，却因为市场画像常见而直接补进简历。
- 事实卡仍为草稿时，系统绕过确认生成可直接导出的正式简历。
- 测试 JD 或其重复版本泄漏进岗位画像集、相似检索基线。

## 合格线

### 单条测试

- 总分至少 16/20。
- A、B、D 三项均不得低于 3 分。
- 不得触发一票否决项。

### 一批测试

- 单条合格率至少 80%。
- 平均总分至少 16 分。
- 虚构、禁止事实引用和测试集泄漏必须为 0 次。
- 每个有足够样本的主要岗位方向都至少包含 2 条测试 JD；不能用某一类岗位的高分掩盖另一类失效。

这些是 V1 的初始门槛。正式评估两轮后，可以根据真实评分分布调整，但必须记录版本和调整原因，不能为了让结果“通过”而临时降低标准。

## 评价流程

1. 冻结测试 JD 和对应重复组，确认它们未参与画像与检索。
2. 在同一个代码版本、同一份个人事实库和同一份原始简历上运行 Agent。
3. 评价者先完成参考答案，再查看输出并逐项评分。
4. 差异性按岗位对评分，其余维度按单条评分。
5. 保存 Agent 版本、画像版本、事实库版本和评分标准版本，确保结果可复现。
6. 汇总平均分、合格率、各维度最低分和严重错误数；先修复严重错误，再优化平均分。
