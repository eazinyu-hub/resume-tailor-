# DeepSeek 简历生成助手 / Agent V1 接入方案

初始设计日期：2026-09-22。接入、候选确认应用与两个脱敏真实调用案例已完成，见 [验收记录](live-demo-acceptance.md)。下文保留当时的实施拆分。

2026-10-10 发布说明：当前发送预览直接展示输入文本，没有自动脱敏器。调用前应清理 JD、事实和市场参考中的个人信息；不能把早期设计里的脱敏目标当成已经实现的保证。

## 1. 目标与难度

收尾目标：同一份已确认项目事实，面对不同岗位，生成侧重点不同、可核对的项目描述，
由用户确认后组成完整简历并导出。优先解决现在描述机械、岗位差异不明显的问题。

整体难度中等：调用接口和读取配置较简单；事实约束、预览确认、错误处理和质量验收是主要工作。
现有导入、画像、检索、事实卡、编辑和导出均可复用，不重建前后端，不承诺接上模型就自动变准。

准确定位是“检索 + 大模型生成 + 程序校验 + 人工确认”的受控工作流。
可以称为 Agent V1，但不宣称具备自主规划、多 Agent 协作或已训练专用模型。

## 2. 已有基础与必须调整的衔接点

- `backend/app/agent_v1.py` 已汇集当前 JD、相似岗位、画像和事实；当前明确是本地规则模式。
- 现有 `prompt_package` 包含较完整的简历和样本，不能直接整体发给外部模型，要新建最小化上下文。
- `grounded_resume.py` 可继续负责把项目内容与本地个人信息、教育、工作经历组装在一起。
- 当前前端生成草稿后立即调用保存接口；模型预览必须与保存分开，不覆盖已有草稿。
- 当前草稿读取只认可 `agent-v1-confirmed-facts` 来源；新增模型来源时需兼容旧稿，不能伪装成旧规则来源。
- 当前草稿保存接受普通内容，不能把前端传入的“已验证”字段或来源标签当作验证凭据。
- 已有评价标准和回归案例可继续使用；README 仍写着初始化骨架，发布前需更新。

## 3. 首版范围

先只接入“AI 简历适配工作台”这个项目，每个目标岗位最多提供两个短版本，
每版 2～3 条项目描述，并附修改原因、事实引用和风险提示。用户选一个版本用于草稿。
两个版本确有必要才返回两个，不为凑数重复改写；事实不足可以返回缺口或不生成。

本次不扩爬虫来源、不做自动投递、不训练模型、不引入向量数据库或复杂 Agent 框架。
不重写学历、工作时间、公司、职位等固定信息；不新增一套简历模板。
面试追问、自我介绍先保留现有输出并标明本地规则模式，不能全部冒充 DeepSeek 生成。

## 4. 用户路径

1. 在当前岗位下选择“AI 生成项目描述”；原有本地规则分析仍可免费使用。
2. 展示将发送的脱敏上下文、外部模型说明及可能消耗 API 额度的提示，用户确认后才请求。
3. 后端检索并冻结当前上下文，调用 DeepSeek，返回候选文本、事实 ID、修改理由和风险。
4. 用户在同一个岗位下查看“原事实 / 候选表述 / 理由”，取消时保留原草稿。
5. 用户选择候选并确认应用；后端重新检查事实版本，再组装、保存该岗位草稿。
6. 沿用现有编辑和 Word / PDF 导出。后续人工编辑要明确是用户修改，不能保留机器验证假象。

切换岗位须取消前端等待并忽略旧响应；每次请求、候选和确认操作都绑定岗位 ID。
前端取消等待不保证供应商取消计算或计费，需要明确说明，不能自动重发。

## 5. 输入、输出与真实性边界

### 输入最小化

- 当前 JD：主要依据，职责、硬要求和加分项分开，不悄悄截断关键要求。
- 相似样本：最多 3～5 条相关片段，沿用去重和测试集排除；不够时不凑数。
- 市场画像：只取同方向必要摘要，标为参考，不能升级成当前岗位硬条件。
- 项目事实：只允许已确认卡片中“已验证且允许写入”的条目及必要限定；保留稳定事实 ID。
- 原简历：首版只取本项目相关文字、表达长度参考；原简历中的假设或十月计划不能升级为事实。
- 姓名、电话、邮箱、照片、详细住址、密钥、本地路径不作为模型输入；教育、工作等固定段落在本地合并。

自动脱敏并非绝对可靠，因此用户能检查实际发送内容；超出上下文预算时提示缩小范围，不静默漏掉 JD。
不发送整个数据库，不把真实素材提交到 GitHub，不宣称第三方调用具有未经核实的零留存保证。

### 结构化输出

每个候选包含：`project_id`、`focus`、`bullets`；每条描述包含 `text`、`fact_ids`、
`jd_evidence` 和 `reason`。另返回必要的 `gaps`、`risks`。
输出只允许纯文本数据，不让模型返回可执行脚本、文件路径、HTML 页面或工具操作。

### 三层检查

1. 输入层过滤：禁止、计划、未确认事实不能进入可引用事实集合；JD 和素材中的指令一律视为数据。
2. 后端结构检查：字段和长度、事实 ID、项目归属、状态与 JD 引文；无有效依据的候选不允许应用。
   检查明显新增数字、工具、上线状态及强措辞，但不把简单关键词检查说成完整语义验证。
3. 人工确认：有效的事实 ID 不等于句子一定被事实支持。并排显示原文，用户检查范围、指标与熟练程度。

模型不生成或修改匹配分数，不改变事实状态，不写数据库，不触发采集、投递或系统命令。
确认应用时重新计算 JD、事实卡、原简历版本摘要；内容变更则阻止应用旧预览，要求重新核对。

## 6. 后端配置、费用和失败处理

### 密钥与运行环境

- 本地密钥预定放 `D:/AI/resume-tailor/backend/.env`，由后端配置模块显式加载。
- 使用 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`；前端不能接收密钥，也不使用 `VITE_` 密钥变量。
- `.gitignore` 忽略 `.env` / `.env.*`，保留无真实值的 `.env.example`；提交前检查暂存区和历史。
- `.env` 是明文配置，不是加密保险箱。进程环境变量优先于本地文件，文件路径基于代码位置，不依赖启动目录。
- 测试禁用真实 `.env` 加载并模拟网络；Linux 使用服务器环境变量及持久化私有 `DATA_DIR`。
- 配置加载要早于现有 `DATA_DIR` 初始化，避免读错库；缺少密钥仅禁用 AI 入口，不影响本地功能。
- 密钥不打印、不回显、不出现在 URL、错误详情、请求日志或浏览器中。
- 供应商目标固定为官方 HTTPS 接口，拒绝重定向；浏览器不得传入任意目标地址或认证头。

公开 GitHub 代码不等于公开付费 API。V1 先保持本地运行；若后续部署到公网，必须另行增加鉴权、
请求校验、用户限额及滥用保护，不能把 CORS 当作鉴权，也不能直接暴露代付接口。

### 调用约束（初始方案，实际联调后可调整）

- 用户确认一次，最多调用一次；单次请求生成两个候选，不为每个版本重复调用。
- 非流式输出，单个进行中的生成任务；重复点击使用请求 ID 去重，刷新/切换岗位不自动调用。
- 建议总等待上限 60 秒、输出上限 2,000 token；给输入设置独立预算，超限提示。
- 超时、余额不足、鉴权失败、限流、空响应、截断、JSON 无效都有清楚提示；首版不自动重试或自我修复循环。
- 用户主动重试可能再次计费；用量使用供应商返回的 usage，不用未经核实的价格换算人民币。
- 失败不覆盖草稿，不偷偷降级成规则结果；用户可主动选择带清楚标签的本地模式。

本地候选记录预定放 `<DATA_DIR>/agent-previews/`，只存必要输出、事实引用、版本摘要、模型/提示词版本和用量；
不记录密钥或完整请求日志，不进入 Git。确认只提交候选 ID，由后端读取校验记录，不能信任客户端自报通过。
生成阶段不修改正式草稿；应用前保存旧草稿的可恢复副本，再使用现有数据库存储新版本。

## 7. 分步实现与完成标志

开始功能开发前，先在用户确认后把已验收的批量/定时采集改动单独提交为恢复点，再开接入分支。
每一小步验收后，由用户决定是否提交，不自动推送 GitHub。

| 步骤 | 本步只做什么 | 可立即验证的完成标志 |
| --- | --- | --- |
| 1. 安全接通 | 后端配置、薄 API 客户端、错误处理和模拟测试；用户本地填写密钥后，用一条无个人信息的测试请求连通 | 前端源码/产物/网络中无供应商密钥；后端收到真实响应；无密钥时原功能可用 |
| 2. 一个项目的候选 | 脱敏预览、事实过滤、一次模型生成、结构校验；在对应岗位下展示最多两个版本，不保存草稿 | 同一项目针对两个 JD 有合理侧重点变化；每条有依据；失败、切换岗位和重复点击不污染结果 |
| 3. 确认后应用 | 用户选择版本，后端复核并应用；兼容旧稿、手动编辑和现有导出 | 取消保留旧稿；过期事实被拦截；确认才替换；两个岗位独立保存，Word / PDF 不回退旧模板 |
| 4. 验收并准备公开 | 固定案例、回归测试、README、脱敏截图和 3 分钟演示 | 新机器按说明能启动；演示完整；失败和边界有说明；无私人数据/密钥；用户确认后才公开 |

主要预计新增后端配置/客户端、上下文与结构校验、生成编排模块；复用 `agent_v1.py`、
`grounded_resume.py`、现有前端岗位面板与草稿编辑区。准确文件拆分在实现时确定，不为了命名先造空架构。
付费生成使用新的 POST 入口，现有 GET 分析接口保持本地、无付费副作用。
现有 `resume_drafts.content_json` 优先扩展版本/来源元数据，不先增加大批业务表。

## 8. 验收标准：证明有用，而不是只证明调用成功

第一对演示：同一组“AI 简历适配工作台”事实，分别对应工具自动化和 Vibe Coding 全栈 JD。
在看输出前由用户标重点：前者关注数据处理、批量与调度；后者关注界面、接口、存储与验证。
只有事实本身支持这些能力时才可以展示；两个岗位共享事实允许重复，不能强行制造不同经历。

发布前最小真实效果验证：固定 4～6 条覆盖不同重点和高门槛缺口的 JD，保持事实和模型配置一致，
与现有规则结果对照，沿用 `docs/agent-evaluation-rubric.md` 的评分与否决标准，不用模型给自己打分。
首版只升级项目部分，未升级的全简历评价项标为未评，不虚报整套评分通过或统计显著提升。
保存输入/模型/提示词版本和必要结果，模型输出不保证逐字复现。

自动测试至少覆盖：无密钥、401/402/429/服务错误、超时、空/截断/非法 JSON、未知或禁止事实、
跨项目引用、提示词注入、重复点击、切换岗位、事实修改后应用、旧稿兼容和导出。
单元测试不访问付费 API；真实小规模效果测试经用户确认后单独执行。

现有规则版最近一次全量测试为 159 项通过（2026-09-21），只作为回归基线，不等于模型效果证明。
公开前一页导出须做版面检查，不能为了容纳过长模型输出不断缩小字体；必要时提示删减。
