# 项目事实卡（4.1 设计）

## 目的

项目事实卡只记录可回溯的真实项目事实，供后续的简历匹配、项目候选版本、面试追问和真实性检查使用。

它不是简历成稿，也不会因为某个 JD 出现了关键词，就把该关键词写进项目经历。

## 一张卡的最小结构

每个项目一张卡，除了项目名称外，使用以下八组字段。

| 字段 | 记录什么 | 填写规则 |
| --- | --- | --- |
| 真实问题 | 谁在什么场景下遇到了什么问题，项目为什么存在 | 不把“想做一个产品”写成真实业务需求；可标注为个人探索 |
| 已完成功能 | 已经实际完成、运行或验证过的功能 | 每项可单独勾选完成度，未完成不写为已交付 |
| 技术与 AI 工具 | 实际直接使用过的语言、框架、服务、AI 工具，以及用在什么环节 | “知道/看过”与“实际用过”分开；工具名不能代替实现细节 |
| 错误与失败 | 报错、失败尝试、限制条件、尚未解决的问题 | 保留失败是为了让面试回答可信，不是负面记录 |
| 调试方法 | 如何定位、修改、验证上述问题 | 至少写清一个输入、一个检查方式或一个验证结果 |
| 当前完成度 | 当前状态、已完成范围、待做范围、最后验证时间 | 使用“原型 / 可运行 / 已验证 / 持续迭代”等事实状态，不用模糊百分比 |
| 展示证据 | 能证明事实的链接或本地证据：Git 提交、仓库、截图、运行命令、Demo、测试结果 | 证据可设为私有，仅在本地个人数据目录保存 |
| 禁止夸大的内容 | 不可写进简历或必须加限定的话 | 例如“没有部署到公网”“没有真实用户”“未独立完成某模块” |

## 必备元信息

为保证以后能定位项目，每张卡还需要：

- `project_id`：稳定的内部编号；不因改名而变化。
- `project_name`：项目名称。
- `project_type`：个人项目、工作项目、练习/复刻、协作项目之一。
- `ownership`：独立完成、主要负责、参与其中之一；协作项目要说明自己负责的部分。
- `fact_status`：草稿、已确认、待核实之一。只有“已确认”的内容才可自动进入简历建议。
- `updated_at`：最后一次核对日期。

## 真实性边界

1. 简历生成只能引用事实卡中“已确认”的条目。
2. “使用 AI 工具”必须能回答：用于哪一步、产出是什么、你如何检查结果。
3. 不能把本地可运行写成“已上线”，不能把个人测试写成“真实用户使用”，不能把参考/复刻写成原创项目。
4. 没有证据不等于不能写，但必须标为“待核实”，不能作为自动强化的卖点。

## 编辑与确认规则

- 页面允许修改、新增和删除事实，并单独维护每项证据状态。
- 任何保存操作都会把整张事实卡恢复为 `draft`，防止修改后的内容沿用旧确认状态。
- “确认事实卡”必须由用户主动点击；确认后，只有证据状态为“已验证”的内容可以进入 Agent。
- 项目事实继续保存在仓库外的 D 盘个人数据目录，Git 只保存字段设计和功能代码。

## 阶段四完成标志

- 字段覆盖项目事实、验证过程与夸大边界。
- 已录入首张“AI 简历适配工作台”事实卡。
- 每条事实具有已验证、需要补充、计划实现或禁止写入简历的状态。
- 页面可维护并确认事实卡；修改后必须重新确认。
